# authentik stage checklist

The exact authentik configuration BSYSTEM expects, and how to verify it before
an acceptance. **No real client secret, key or password appears here**, and none
should be added — the HUB uses a public client with PKCE and therefore has no
client secret at all.

`docs/AUTHENTIK-OIDC.md` describes the same setup for local development. This
document is the stage-specific version: what differs, what must match exactly,
and what to test.

## 1. Groups

Create these eight groups. The names are matched **exactly and
case-sensitively** against `group_role_mappings` in the Integration Core; a
group named `BSYSTEM-admins` maps to nothing, and a user in it resolves to no
roles and is denied everywhere.

| Group | BSYSTEM role |
| --- | --- |
| `BSYSTEM-Admins` | administrator |
| `BSYSTEM-Managers` | manager |
| `BSYSTEM-Developers` | developer |
| `BSYSTEM-QA` | qa |
| `BSYSTEM-Support` | support |
| `BSYSTEM-DevOps` | devops |
| `BSYSTEM-Customers` | customer (scope-confined) |
| `BSYSTEM-Services` | service identity |

A principal in no BSYSTEM group is not an error state to fix: it resolves to no
roles, no permissions and no modules, and is denied everywhere. That is the
deny-by-default rule working, and it is one of the cases the acceptance tests.

## 2. Application and provider

| Setting | Value |
| --- | --- |
| Application name | `BSYSTEM-HUB` |
| Application slug | `bsystem-hub` |
| Provider type | OAuth2/OpenID Provider |
| Client type | **Public** (Authorization Code + PKCE) |
| Client ID | generated by authentik; goes into `VITE_OIDC_CLIENT_ID` |
| Client secret | **none** — a public client has no secret |
| Issuer / authority | `https://id.stage.example/application/o/bsystem-hub/` |

The issuer is the value that goes into `VITE_OIDC_AUTHORITY`, **including the
trailing slash**. An issuer mismatch produces a token the platform rejects with
no useful message, and it is the most common OIDC misconfiguration there is —
which is why the preflight fails on a missing trailing slash rather than
warning about it.

Remember that `VITE_*` values are **build-time** arguments for the HUB image.
Changing the client id means rebuilding the HUB, not restarting it.

## 3. Redirect and logout URIs

| Purpose | Value |
| --- | --- |
| Redirect URI | `https://hub.stage.example/callback` |
| Post-logout redirect URI | `https://hub.stage.example/` |

Use exact URIs, not wildcards. A wildcard redirect URI in an OAuth2 public
client is an open redirect: an attacker who can get a user to start a sign-in
can have the authorization code delivered to a host of their choosing. This is
worth being strict about even in stage, because stage configuration is what
gets copied into production.

## 4. Scopes

| Scope | Why |
| --- | --- |
| `openid` | required |
| `profile` | display name and username |
| `email` | email address |

BSYSTEM needs no other scope. Adding more sends the HUB claims it does not use
and cannot protect.

## 5. Claims BSYSTEM reads

From the UserInfo response, server-to-server:

| Claim | Used as | Required |
| --- | --- | --- |
| `sub` | the stable subject; the identity's primary key | **yes** |
| `groups` | role resolution, matched against the table above | yes in practice |
| `email` | display and audit | no |
| `name` | display name | no |
| `preferred_username` | display | no |

`sub` must be **stable for the life of the account**. A Global ID (`USR-*`) is
allocated against it and is immutable; if `sub` changes, the same person
becomes a second identity with a second Global ID, and everything recorded
against the first — audit, scope grants, notification reads — stays attached to
an identity nobody can sign in as.

`groups` must actually be in the UserInfo response. authentik does not always
include it by default: a property mapping may be required. This is the single
most common cause of "the user signs in successfully but sees nothing", and it
is indistinguishable from a permissions problem unless you check.

## 6. Service identities

Service identities are machine callers. They sign in with the client-credentials
flow and must be in `BSYSTEM-Services`.

| Requirement | Detail |
| --- | --- |
| Group | `BSYSTEM-Services` |
| Token | client credentials, not a user session |
| Global ID | `SVC-*`, allocated on first call |
| Surface | `/api/service/v1/*` only |

A service identity is not a human with extra rights, and a human token does not
reach the machine API. The smoke runner marks machine-API checks as SKIP when
it has no service token, rather than asking for the boundary to be widened.
Do not grant a human account `BSYSTEM-Services` to make an acceptance
convenient: that is exactly the boundary being accepted.

## 7. What the Integration Core needs to reach

`AUTHENTIK_USERINFO_URL` must resolve **from inside the Core's container**:

```text
http://authentik-server:9000/application/o/userinfo/
```

This is usually not the public issuer URL. If the Core is given the public URL
and egress to it is blocked, every sign-in fails at UserInfo with a timeout,
while authentik itself looks perfectly healthy from a browser.

## 8. Test checklist

### MFA

- [ ] an MFA stage is bound to the authentication flow
- [ ] a user with MFA enrolled is prompted, and the HUB completes the flow
- [ ] a user who cancels MFA does **not** reach the HUB
- [ ] recovery/backup codes work, and using one is visible in authentik's log
- [ ] MFA cannot be skipped by going straight to the Core's API with an old
      token — confirm the token's lifetime is what you think it is

### Customer user

- [ ] a user in `BSYSTEM-Customers` **and no other BSYSTEM group** signs in
- [ ] the HUB shows only the modules that user's role resolves to
- [ ] `GET /api/v1/me` reports the customer role and nothing more
- [ ] a client the user does not own returns 404, not 403 — existence is not
      disclosed
- [ ] with no scope grant, every scoped collection is empty rather than
      forbidden, and no record from another customer appears

The last two are the isolation properties. Until the authoritative ownership
mapping exists they cannot be fully tested; see
[`TENANT-ISOLATION-MATRIX.md`](TENANT-ISOLATION-MATRIX.md).

### Service identity

- [ ] a client-credentials token is issued for an identity in `BSYSTEM-Services`
- [ ] `GET /api/service/v1/whoami` returns an `SVC-*` Global ID
- [ ] the same token is **rejected** on `/api/v1/*` — the human surface
- [ ] a human token is **rejected** on `/api/service/v1/*`
- [ ] an identity outside `BSYSTEM-Services` is rejected on the machine API

### Negative cases

- [ ] no token → 401 on every `/api/v1/*` and `/api/service/v1/*` endpoint
- [ ] expired token → 401, not 500
- [ ] a user in no BSYSTEM group signs in and sees nothing, without an error
- [ ] a malformed `Authorization` header → 401
- [ ] `/health`, `/readyz` and `/metrics` answer **without** a token; that is
      deliberate, and they disclose no customer data

## 9. What stays blocked

- the real issuer hostname and the HUB's public URL
- the generated client id
- which authentik users belong to `BSYSTEM-Customers`, and which client each of
  them owns

The last one is the ownership mapping. Without it, customer isolation can be
tested for *deny* behaviour but not for *allow* behaviour: it can be shown that
a customer sees nothing they should not, but not yet that they see everything
they should.

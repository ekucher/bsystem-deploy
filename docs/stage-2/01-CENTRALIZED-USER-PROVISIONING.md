# ТЗ: Централізоване керування користувачами для Redmine / QA / Nextcloud / Outline

**Status:** Draft — потребує проєктування точних API-контрактів (розділ 9) перед реалізацією
**Stage:** Stage 2 (залежить від HUB — див. `docs/stage-2/README.md` щодо співвідношення з `S1-INV-02`)
**Date:** 2026-09-27

## 1. Мета

Дати можливість створювати людину-користувача **в одному місці** (сторінка `/admin/accounts` у `bsystem-hub`) і одразу отримувати робочий обліковий запис із базовою роллю в чотирьох нативних застосунках — Redmine, QA, Nextcloud, Outline — без ручного створення в кожному окремо.

Кожен застосунок лишається повністю автономним у власній моделі ролей і прав: централізується **лише факт існування акаунта та грубий стартовий доступ**, ніколи — детальна авторизація всередині застосунку (членство в проєктах Redmine, колекціях Outline, файлові ACL Nextcloud тощо).

## 2. Поточний стан (факт, перевірено в коді)

| Застосунок | Механізм входу сьогодні | Створення акаунта сьогодні |
|---|---|---|
| **Redmine** | Вже є lazy SSO через сторонній плагін `kontron/redmine_oauth` (окремо від власного репозиторію `redmine_bsystem_integration`, який відповідає лише за Related Objects) | Ручне (або авто через сторонній плагін — точна поведінка не перевірена в цьому репо) |
| **QA** | Власний OIDC-код (`lib/oidc.js`) | Явно ВІДМОВЛЯЄ авто-створення (`resolveSsoUser` повертає `null`, якщо немає збігу за subject/username) — лише ручне через адмін-панель |
| **Nextcloud** | `bsystem_sso` (власний, тонкий) — лише редирект-синхронізація сесії; фактичний OIDC-логін і можливе авто-створення — у вбудованому `user_oidc` (сторонній, налаштовується поза репозиторієм) | Невідомо/не задокументовано в репо |
| **Outline** | Стандартна OIDC-реєстрація застосунку в Authentik, логін через власний вбудований OIDC-плагін Outline | Невідомо/не задокументовано в репо |

`bsystem-integration-core` вже має робочий централізований потік створення людини **на рівні Authentik** (`POST /api/v1/admin/accounts` → створює користувача в Authentik + Global ID `USR-*` + платформну роль `HumanRole`), яким уже керує сторінка `Users.tsx` у HUB. Це не поширюється на жоден із чотирьох нативних застосунків.

Adapters у `bsystem-integration-core` (Redmine/Outline/EspoCRM) сьогодні **лише читають** дані (List/Get) — жодного write/create-методу для акаунтів немає в жодному з них.

## 3. Функціональні вимоги

### FR-1. Єдина точка створення
Адміністратор створює людину один раз через існуючу форму HUB (`Users.tsx` → `POST /api/v1/admin/accounts`), вказуючи ім'я, логін, платформну роль (Authentik-групу).

### FR-2. Негайне (eager) провіжининг для Redmine, Outline, Nextcloud
Одразу після успішного створення користувача в Authentik, у межах **того самого HTTP-запиту**, система повинна створити відповідний акаунт у Redmine, Outline та Nextcloud, з роллю/групою за таблицею мапінгу (розділ 5). Результат кожного застосунку повертається одразу в відповіді (`created` / `failed` / `skipped`).

### FR-3. Відкладене (lazy) провіжининг для QA
QA не має вхідного (inbound) admin API, тому створення QA-акаунта відбувається автоматично **при першому успішному SSO-вході** цієї людини в QA — не потребує окремої дії адміністратора, але акаунт з'являється не миттєво, а в момент першого входу.

### FR-4. Мапінг ролі за Authentik-групою
Стартова роль/група в кожному застосунку виводиться з Authentik-групи людини за фіксованою таблицею (розділ 5), без ручного вибору ролі окремо для кожного застосунку.

### FR-5. Обробка часткової відмови
Якщо один із трьох eager-застосунків тимчасово недоступний під час створення — це **не повинно** скасовувати вже створений акаунт в Authentik чи в інших застосунках. Має існувати спосіб повторити провіжининг для конкретного застосунку окремо (retry), без повторного створення всієї людини.

### FR-6. Видимість статусу (панель у HUB)
Розширення вже наявної сторінки `Users.tsx`/`/admin/accounts`: для кожної людини видно, у яких застосунках є акаунт і яка там роль — без потреби заходити в кожен застосунок окремо для перевірки.

## 4. Нефункціональні вимоги / обмеження

- **NFR-1 (архітектурний інваріант, не підлягає зміні):** жоден застосунок не втрачає власної авторитетності над своєю моделлю ролей/прав. Ця робота торкається лише "акаунт існує + грубий стартовий доступ".
- **NFR-2:** жодних прямих cross-system джойнів баз даних (QA не пише напряму в БД Integration Core; взаємодія — лише через API/сервісну ідентичність).
- **NFR-3 (безпековий інваріант):** роль/рівень доступу "адміністратор" у QA **ніколи** не надається автоматично, за жодною групою, включно з BSYSTEM-Admins. Це узгоджується з уже існуючим у QA запобіжником проти ескалації прав через самостійну зміну username в Authentik.
- **NFR-4:** створення акаунтів у зовнішніх системах — best-effort, синхронно в межах запиту (не через чергу подій) — адміністратор має бачити результат одразу, а не "ймовірно з'явиться пізніше". Компроміс: складніша обробка часткової відмови (FR-5) замість простішої, але повільнішої з точки зору UX подієвої моделі.
- **NFR-5:** кожен новий зовнішній admin-клієнт (Redmine/Outline/Nextcloud) — незалежно опціональний; відсутність налаштування облікових даних для одного застосунку не повинна блокувати створення в інших.
- **NFR-6:** усі нові облікові дані (API-ключі адмін-доступу до Redmine/Outline/Nextcloud) — класифікація CREDENTIAL, ніколи не комітяться в git, тільки через `.env`.

## 5. Мапінг Authentik-групи → роль/доступ у кожному застосунку

| Authentik-група | Redmine | Outline | Nextcloud | QA |
|---|---|---|---|---|
| **BSYSTEM-Admins** | Admin-tier роль (авто-ескалація) | Workspace-admin (авто-ескалація) | група `admin` (авто-ескалація) | `viewer` — **адмін ніколи не автоматично** |
| BSYSTEM-Managers | Reporter | Member | `users` | `project_manager` |
| BSYSTEM-Developers | Developer | Member | `users` | `developer` |
| BSYSTEM-QA | Reporter | Member | `users` | `tester` |
| BSYSTEM-Support | Reporter | Member | `users` | `viewer` |
| BSYSTEM-DevOps | Developer | Member | `users` | `developer` |
| **BSYSTEM-Customers** | `skipped` (акаунт не створюється) | акаунт створюється (документація) | `skipped` | `skipped` |

Примітка: "роль" тут означає лише стартовий, грубий рівень доступу застосунку в цілому. Членство в конкретних проєктах Redmine чи конкретних колекціях Outline — окреме, ручне рішення адміністратора відповідного застосунку, поза межами цього ТЗ.

## 6. Інтерфейси / контракти даних (для проєктування)

### 6.1. Розширення відповіді `POST /api/v1/admin/accounts`
Додається поле:
```json
"native_apps": [
  { "app": "redmine",   "status": "created", "role": "developer" },
  { "app": "outline",   "status": "created", "role": "member" },
  { "app": "nextcloud", "status": "failed",  "error": "timeout" }
]
```
`status` ∈ `created | failed | skipped`. `skipped` — коли застосунок не отримує акаунт для цієї групи (розділ 5) або коли admin-креденшали для цього застосунку не налаштовані в середовищі.

### 6.2. Новий ендпоінт: retry для одного застосунку
`POST /api/v1/admin/accounts/{id}/native-apps/{app}/retry` — повторює спробу створення лише для вказаного застосунку, використовуючи вже існуючу Authentik-групу людини для повторного визначення ролі.

### 6.3. Новий ендпоінт: підтвердження від QA
`POST /api/v1/admin/accounts/{id}/native-apps/qa/ack` — QA викликає це одразу після успішного локального авто-створення (крок FR-3), авторизовано як сервісна ідентичність QA, щоб панель видимості (FR-6) знала про QA-акаунт без прямого доступу до бази Integration Core.

### 6.4. Зовнішні API, якими будуть керуватись нові клієнти (потребують живої перевірки перед реалізацією — нижче не факт із цього репозиторію, а відоме публічне API кожного продукту)
- **Redmine**: REST `POST /users.json`, автентифікація `X-Redmine-API-Key` (адмінський API-ключ).
- **Outline**: `POST /api/users.invite`, bearer-token (персональний API-ключ адміністратора).
- **Nextcloud**: OCS Provisioning API `POST /ocs/v2.php/cloud/users`, HTTP Basic (адмін-користувач + app password), заголовок `OCS-APIRequest: true`.

### 6.5. Нові змінні оточення
`REDMINE_ADMIN_URL`, `REDMINE_ADMIN_API_KEY`, `OUTLINE_ADMIN_URL`, `OUTLINE_ADMIN_API_TOKEN`, `NEXTCLOUD_ADMIN_URL`, `NEXTCLOUD_ADMIN_USER`, `NEXTCLOUD_ADMIN_APP_PASSWORD` — усі CREDENTIAL, лише в `.env`, ніколи в git.

### 6.6. QA: розширення OIDC-скоупу
Authentik-клієнт QA сьогодні не запитує claim `groups` — без цього QA не може визначити роль за таблицею мапінгу. Потрібне розширення scope в blueprint QA-провайдера.

## 7. Поза межами ТЗ (свідомо)

- Членство в конкретних проєктах Redmine, колекціях Outline, файлові права Nextcloud.
- Власна детальна модель прав QA (`can.*`) за межами грубого стартового `role`.
- Уніфікація ролей у єдину крос-платформну концепцію ("розробник скрізь однаково").
- Зміна моделі груп у самому Authentik.
- Подієво-орієнтована (NATS) архітектура провіжинингу — свідомо відхилена на користь синхронної (розділ NFR-4).

## 8. Критерії приймання

1. Створення людини з роллю `developer` (група BSYSTEM-Developers) у HUB — у відповіді того ж запиту `redmine/outline/nextcloud: created`, підтверджено напряму в адмін-панелі кожного застосунку.
2. Людина в групі BSYSTEM-Admins отримує адмінський доступ автоматично в Redmine/Outline/Nextcloud, але **ніколи** — `admin` у QA.
3. Людина в групі BSYSTEM-Customers отримує акаунт лише в Outline; в інших трьох застосунках акаунт не створюється.
4. При недоступності одного із зовнішніх API під час створення — решта застосунків та сам Authentik-акаунт створюються успішно; повторна спроба через retry-ендпоінт доводить пропущений застосунок до `created` без повторного створення людини.
5. Перший SSO-вхід нової людини в QA автоматично створює акаунт із коректною роллю; повторний вхід прив'язується до того самого акаунта, не створює дублікат.
6. Панель `/admin/accounts` у HUB показує статус по всіх чотирьох застосунках без додаткової дії "оновити".

## 9. Відкриті питання для проєктувальника

- Точні request/response-схеми Redmine/Outline/Nextcloud admin API (розділ 6.4) — потребують живої перевірки проти реально розгорнутих версій перед фіксацією контракту.
- Чи потрібне обмеження на повторні retry (rate-limit), якщо зовнішній застосунок довго недоступний.
- Формат зберігання статусу для панелі видимості (розділ FR-6) — окрема кеш-таблиця чи розширення наявної моделі ідентичності в Integration Core.
